# Журнал расхождений и уточнений относительно ЛР № 2

Журнал фиксирует каждое осознанное изменение между проектом ЛР № 2 и реализацией ЛР № 3. Краткий реестр всех пунктов размещён на первой странице отчёта; здесь приведены причина, граница и влияние на безопасность.

| ID | Решение / ожидание ЛР № 2 | Реализация ЛР № 3 | Причина | Влияние и контроль |
|---|---|---|---|---|
| CH-01 | Стек API/worker в проектном варианте ЛР № 2 | API и worker реализованы на Go 1.25 | Прямое требование пользователя; язык разрешено выбирать в ЛР № 3 | API-контракты, модель данных, роли, Redis, RabbitMQ и общая топология сохранены |
| CH-02 | Отдельный LLM Gateway и внешний провайдер | Авторизованный endpoint AI-проверки возвращает 501; контейнеры LLM не запускаются | Прямое исключение в задании ЛР № 3 | Не влияет на оценку согласно заданию; маршрут остаётся в API-контракте |
| CH-03 | `notifications` не идентифицировала исходное outbox-событие | Добавлено `source_outbox_event_id UUID UNIQUE` с FK на `outbox_events` | Дедупликация повторного сканирования outbox | Одна строка уведомления на событие; это DDL-изменение отражено в схеме и отчёте |
| CH-04 | Внешняя HTTPS/JSON-интеграция почты | Worker отправляет SMTP в локальный Mailpit | Задание ЛР № 3 допускает локальную почтовую заглушку | Email остаётся асинхронным, сообщения можно просматривать в UI; внешняя доставка не заявляется |
| CH-05 | Redis предусмотрен для сессий, лимитов и кэша | Реализованы opaque-сессии, Redis Lua fixed-window rate limiting и кэш типа документа TTL 5 минут | Необходимо реально использовать технологию из диаграммы | При недоступности Redis контролируемые запросы завершаются 503, а не обходят лимиты |
| CH-06 | Минимальные права для сервисных соединений | Роли `documents_app` и `documents_worker` имеют раздельные GRANT | Принцип наименьших привилегий | Worker не может менять пользователей, заявки или документы; API/worker не имеют DDL-прав |
| CH-07 | Восстановление доступа предполагает отправку письма | Код восстановления выводится в журнал API как локальная заглушка | Допускается заданием ЛР № 3 | В БД хранится только SHA-256 кода; TTL 20 минут, код одноразовый; логирование допустимо только в учебной локальной среде |
| CH-08 | В межсервисных потоках ЛР № 2 указан TLS | В локальном Compose внутренний TLS не настроен | Упрощение воспроизводимого учебного развёртывания | Все опубликованные порты привязаны к localhost; перед production нужен TLS и хранилище секретов |
| CH-09 | Для некоторых отказов контракт допускает 403/404; чужой объект можно маскировать | USER получает 404 для чужой заявки/документа; ADMIN вне scope получает 403 | Анти-enumeration для USER и явный контроль подразделения для ADMIN | Проверка владельца/scope выполняется сервером; один UUID не даёт права доступа |
| CH-10 | Создание не должно принимать от клиента владельца, статус, роль и timestamps | JSON-декодер отклоняет все неизвестные поля | Защита от mass assignment | Атакующий запрос получает 400; корректный запрос использует серверные owner/status |
| CH-11 | События аудита предполагают `request_id`, но клиент может его не передать | Middleware генерирует UUID при отсутствующем/невалидном `X-Request-ID` | Устойчивость корреляции событий | Один UUID возвращается в HTTP-ответе и используется при записи событий |
| CH-12 | Контракт выдачи содержит `document_title`; чтение возвращает тело документа | Название обязательно и нормализуется; бинарное содержимое передаётся Base64 | Исполнение контракта для `BYTEA` | Не требуется менять поле БД; документ остаётся учебным текстовым артефактом |
| CH-13 | Диаграмма последовательности показывает публикацию уведомления после записи outbox | Outbox publisher и consumer размещены в отдельном worker; публикация persistent AMQP сообщения ждёт confirmation | Изоляция асинхронной обработки от HTTP-транзакции | Уведомление доставляется после commit; модель — at-least-once; фактическая архитектура отражена отдельной диаграммой |
| CH-14 | Inline JS/CSS несовместимы со строгой CSP | Скрипт/стили вынесены в `web/app.js` и `web/style.css`; CSP задана Nginx и API | CSP должна применяться также к статическому клиенту | UI не нуждается в `unsafe-inline`; обработчики используют `data-action` |
| CH-15 | Для POST создания допускается защита от сетевых повторов через `Idempotency-Key` | Добавлены `applications.idempotency_key` и `idempotency_payload_hash`, уникальность в пределах владельца и проверка fingerprint | Защита retry без изменения семантики POST при отсутствии заголовка | Повтор с тем же ключом/телом возвращает исходную заявку; ключ с другим телом приводит к 409 |
| CH-16 | Ошибки БД и отказ зависимостей требуют предсказуемого поведения | 404 отделён от инфраструктурной ошибки; сброс пароля откатывается при недоступном Redis; сессии отзываются до commit; SMTP retry задерживается на 2 секунды | Усиление отказоустойчивости и безопасного поведения при сбоях | Не выдаётся ложный 404 при сбое БД; не коммитится reset при невозможности отозвать сессии; предотвращается горячий цикл повторной доставки |

## Ограничения, не скрываемые в отчёте

Перечисленные изменения не означают production readiness. LLM пропущена по прямому условию; восстановление доступа использует локальный лог вместо реальной почты; внутренние каналы Compose не используют TLS; выдаваемый учебный текст не включает вид электронной подписи или нормативный формат. ЛР № 1–2 не задают конкретный юридический механизм, поэтому хеш документа не объявляется доказательством его юридической силы.
