# Реестр статической проверки и сценариев проверки ЛР № 3

## Ограничения текущей среды проверки

Проверка выполнялась в контейнерной среде подготовки артефактов. В ней установлен Go `1.23.2`, тогда как проект намеренно закреплён на Go `1.25.0`. Автоматическая загрузка Go 1.25 через `golang.org/toolchain` завершилась ошибкой DNS/сети (`proxy.golang.org` недоступен). Команда `docker` в среде отсутствует. Поэтому сборка Go 1.25, `docker compose build/up` и интеграционные запросы к живым PostgreSQL/Redis/RabbitMQ здесь **не выполнялись**. Этот факт не маскируется под успешный runtime-тест; живую проверку необходимо выполнить на машине с Docker Compose v2 и доступом к registry.

## Автоматизированные unit-тесты в `api/main_test.go`

Тесты покрывают:

- проверку формата UUID;
- отклонение неизвестных JSON-полей (mass assignment) и нескольких JSON-значений в одном теле;
- кодирование Argon2id с ожидаемыми параметрами стоимости и проверку правильного/неправильного пароля и pepper.

Они должны быть исполнены после получения Go 1.25 и модулей командами `cd api && go test ./...` и `cd worker && go test ./...` либо через CI.

## End-to-end проверка на целевом компьютере

Из корня проекта после настройки `.env` и `docker compose up --build -d` выполнить:

```sh
curl -i http://localhost:8080/healthz
./requests/smoke.sh
```

Скрипт `requests/requests.http` содержит ручные запросы ко всем маршрутам; `requests/smoke.sh` содержит следующие проверяемые утверждения, которые являются **ожидаемыми результатами сценариев, а не результатами фактического запуска в этой среде**:

| Сценарий | Ожидаемый результат по реализации/контракту | Что демонстрируется |
|---|---|---|
| USER читает чужую заявку с валидным токеном | `404` | Маскировка существования чужого объекта; серверная проверка владельца |
| USER создаёт заявку с `owner_user_id`, `status`, `role` и другими лишними полями | `400`; INSERT не производится | Запрет mass assignment через allow-list/строгий JSON decoder |
| USER повторяет POST с тем же `Idempotency-Key` и тем же телом | `201`, тот же application_id, одна строка в БД | DB-backed защита сетевого повтора; иной payload с этим ключом должен дать `409` |
| Валидный POST создания от USER | `201`; строка БД содержит серверные `owner_user_id` и `submitted` | Субъект и начальный статус получены не из тела клиента |
| USER вызывает смену статуса | `403` | RBAC проверяется сервером, даже если запрос отправлен в обход UI |
| ADMIN переводит заявку `submitted -> in_review -> approved` | `200` на каждом допустимом переходе | Область подразделения, конечный автомат, транзакция и аудит |
| ADMIN повторяет выдачу после успешной выдачи | Первый POST `201`, повторный `409` | Блокировка, проверка статуса и UNIQUE(application_id) |
| Владелец читает выданный документ | `200` | Содержимое Base64 и hash отданы только после проверки права |
| Другой USER читает документ | `404` | Объектная авторизация документа |
| Брокер доставляет уведомление | Сообщение в `document.notifications`; worker отмечает notification `sent`; письмо видно в Mailpit | Outbox, publisher confirm, ACK и SMTP-заглушка |
| Роль API пытается выполнить `DROP TABLE` или `CREATE TABLE` | Ошибка прав PostgreSQL | Принцип наименьших привилегий |

## Что приложить к отчёту после запуска на компьютере

Для окончательного подтверждения runtime необходимо сохранить в `docs/evidence/` фактические выводы `docker compose ps`, `curl /healthz`, `./requests/smoke.sh`, запросов о правах БД и очереди RabbitMQ. В текущий артефакт не включены фиктивные логи или скриншоты, якобы полученные из не запущенной системы.

Дополнительная обработка ошибок: при инфраструктурной ошибке чтения токена сброса возвращается 500 (а не маскируется как недействительный код); если Redis недоступен при подтверждении смены пароля, операция не коммитится, чтобы не оставить действующие сессии со старым паролем. SMTP retry имеет базовую задержку 2 секунды, чтобы не создавать горячий цикл повторной доставки.
