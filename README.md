# Система заявок на справки и документы — ЛР № 3

Локальная реализация проекта ЛР № 2 для варианта 1 («Заявки на справки и документы», особенность — юридическая значимость выдаваемого документа). Backend и worker написаны на **Go 1.25**. Система запускается Docker Compose и включает PostgreSQL, Redis, RabbitMQ, Mailpit, API, фонового worker и веб-клиент.

## 1. Требования

- Docker Engine с Compose v2.
- 4 ГБ свободной оперативной памяти; интернет-доступ нужен только для первого получения базовых образов и Go-модулей.
- На хосте для ручной проверки: `curl`, `jq` и `docker compose`.
- Go локально не нужен для штатного запуска: сборка Go 1.25 выполняется внутри многостадийных Dockerfile. Локальная сборка вне Docker требует Go 1.25.

## 2. Первый запуск

Из корня проекта:

```sh
cp .env.example .env
```

Измените в `.env` все демонстрационные секреты: `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `WORKER_DB_PASSWORD`, `PASSWORD_PEPPER` (не менее 32 байт), `REDIS_PASSWORD` и `RABBITMQ_PASSWORD`. Строки подключения должны соответствовать именам пользователей и паролям. Для простоты локального примера используйте URL-безопасные значения паролей в URI подключения.

Запуск и проверка готовности:

```sh
docker compose up --build -d
docker compose ps
curl -i http://localhost:8080/healthz
```

Откройте:

| Компонент | Адрес на хосте | Назначение |
|---|---|---|
| Web-клиент | http://localhost:8081 | Основные сценарии пользовательской и привилегированной ролей |
| Backend API | http://localhost:8080 | REST API; health check — `/healthz` |
| Mailpit | http://localhost:8025 | Перехваченные локальные email-уведомления |
| RabbitMQ Management | http://localhost:15672 | Очередь `document.notifications` и состояние брокера |
| PostgreSQL | внутренний адрес Compose `db:5432` | Источник бизнес-истины; порт БД не опубликован наружу |
| Redis | внутренний адрес Compose `redis:6379` | Opaque-сессии, лимиты запросов, кэш справочника типов документов |

Сервисы, опубликованные на хосте, привязаны к `127.0.0.1`.

## 3. Остановить и сбросить данные

```sh
docker compose down
```

Полное удаление состояния PostgreSQL и Redis (команда необратимо удаляет локальные данные стенда):

```sh
docker compose down -v
docker compose up --build -d
```

DDL выполняется автоматически только при первой инициализации volume PostgreSQL: `db/schema.sql`, затем `db/roles.sql` и `db/03_worker_role.sh`. Изменения DDL после первого запуска не накатываются автоматически; для учебного чистого развёртывания используйте `down -v`.

## 4. Тестовые учётные записи

| Роль | Логин | Пароль | Возможности |
|---|---|---|---|
| USER | `student01` | `Student-Demo-2026!` | Создание и чтение своих заявок/документов |
| USER | `student02` | `Student-Demo-2026!` | Второй владелец для проверки горизонтального обхода доступа |
| ADMIN (R-03) | `staff01` | `Staff-Demo-2026!` | Заявки подразделения, смена статуса, выдача, бизнес-аудит |
| TECH (R-04) | `tech01` | `Tech-Demo-2026!` | Только ограниченный набор технических событий аудита через API |

Пароли приведены исключительно для изолированного учебного стенда. Их verifier создаётся при первом запуске API на основе Argon2id и `PASSWORD_PEPPER`; открытые пароли в PostgreSQL не записываются. В production тестовые аккаунты необходимо удалить или заменить управляемой процедурой начального администрирования.

## 5. Реализованные операции

| Операция | Метод и путь | Основные ограничения |
|---|---|---|
| OP-01 | `POST /api/v1/auth/login` | Argon2id; одинаковое сообщение для неизвестного логина и неверного пароля; сессия opaque bearer в Redis |
| Выход | `POST /api/v1/auth/logout` | Удаление серверной сессии из Redis |
| Восстановление | `POST /api/v1/auth/recovery` | Одноразовый код, TTL 20 минут, hash кода в БД, общий ответ без раскрытия существования пользователя |
| Подтверждение восстановления | `POST /api/v1/auth/recovery/confirm` | Код срабатывает один раз; после смены пароля предпринимается отзыв активных сессий |
| OP-02 | `GET /api/v1/applications/{application_id}` | Проверка владельца USER или scope подразделения ADMIN; чужой объект USER маскируется как 404 |
| OP-03 | `POST /api/v1/applications` | Владелец и начальный статус задаются сервером; JSON-декодер отклоняет неизвестные поля; optional `Idempotency-Key` защищает ретраи |
| OP-04 | `PATCH /api/v1/applications/{application_id}/status` | Только ADMIN своего подразделения; конечный автомат статусов; обязательная причина отклонения/отмены; транзакция и outbox |
| OP-05 | `GET /api/v1/applications` | Фильтры статус/тип/диапазон времени, пагинация, page size 1–100, object-level scope |
| OP-06 | `POST /api/v1/applications/{application_id}/issue` | Только ADMIN в своём scope; заявка должна быть `approved`; `FOR UPDATE`, `UNIQUE(application_id)`, документ, история, аудит и outbox в одной транзакции |
| OP-07 | `GET /api/v1/documents/{document_id}` | Проверка владельца или scope; тело возвращается Base64, SHA-256 — отдельным полем |
| OP-09 | `GET /api/v1/audit/events` | ADMIN видит бизнес-аудит; TECH — ограниченные технические события |
| Исключение ЛР №3 | `POST /api/v1/applications/{application_id}/ai/completeness-check` | Авторизованная заглушка с HTTP 501; интеграция LLM намеренно не реализуется по заданию |

Для `POST /api/v1/applications` необязательный заголовок `Idempotency-Key` (8–128 символов) связывается в PostgreSQL с владельцем и SHA-256 fingerprint канонического тела. Повтор с тем же ключом и телом возвращает ту же заявку (`Idempotency-Replayed: true`); повтор ключа с другим содержимым возвращает 409. Без заголовка сохраняется стандартная семантика создания новой заявки.

Точечные лимиты Redis: вход — 10 запросов/мин на IP; создание — 5/мин и 30/час на пользователя; список — 60/мин; чтение заявки/документа — 100/мин; смена статуса — 20/мин; выдача — 5/мин; восстановление — 5 запросов/мин на IP. При недоступности Redis ограничиваемые операции завершаются `503`, а не обходят контроль.

## 6. Безопасность и архитектурные решения

- **Пароли:** Argon2id, `m=65536 KiB, t=3, p=2, key=32 bytes`, случайная соль 16 байт внутри сохранённого verifier; pepper из окружения. При несуществующем логине выполняется dummy verification, чтобы снизить очевидную разницу по времени ответа.
- **Сессии:** случайный 256-битный opaque bearer token; данные сессии и TTL хранятся в Redis; в токене нет доверяемой клиентской роли. Logout удаляет серверную сессию.
- **Object-level authorization:** сервер извлекает `user_id` и роль из сессии. Клиент не может задать `owner_user_id`, `status`, роль, время создания, автора выдачи или хеш документа.
- **SQL:** все данные передаются параметрами `$1...`; нет конкатенации SQL из пользовательского ввода. Клиент БД — отдельная роль `documents_app`, без `CREATE`, `DROP` и `DELETE`. Worker — другая роль `documents_worker` с более узким набором привилегий.
- **Юридически значимая выдача:** блокировка заявки в транзакции, допустимость только из `approved`, уникальность документа на заявку, фиксация истории/аудита/outbox. PostgreSQL-триггеры запрещают менять существенные реквизиты выданного документа и физически удалять документы; событие выдачи и аудит защищены от UPDATE/DELETE.
- **SHA-256:** помогает обнаруживать изменение байтов и связывает событие выдачи с содержимым. Сам по себе хеш не является электронной подписью и не подтверждает юридическую силу документа.
- **Redis:** opaque-сессии, ограничители частоты и кэш типа документа на 5 минут. Ключи персональных сессий включают user ID; в кэше справочника нет персональных данных.
- **RabbitMQ/Outbox:** событие создаётся в той же транзакции, что и изменение статуса/выдача; worker публикует persistent AMQP-сообщение и ждёт publisher confirmation. `source_outbox_event_id` уникален в notifications, чтобы повторное чтение outbox переиспользовало одну запись уведомления. Для клиентских повторов POST создания заявки предусмотрен отдельный DB-backed `Idempotency-Key`.
- **Email:** worker отправляет через SMTP в Mailpit; сообщения перехватываются и доступны в UI. Доставка уведомления асинхронна и не откатывает успешно зафиксированную выдачу.
- **Ошибки:** клиент получает нейтральные сообщения, исключения журналируются на сервере. В HTTP-ответ не передаются SQL, stack trace, пароли или password hash.
- **Заголовки:** request ID генерируется/нормализуется на сервере в UUID; возвращается в заголовке `X-Request-ID`. API и Nginx задают `nosniff`, `DENY`, `no-store` и строгую CSP; клиентские JS/CSS вынесены во внешние файлы, `unsafe-inline` не требуется.

## 7. Проверка сценариев

Запускать из корня репозитория после `docker compose up --build -d`. Полная ручная коллекция всех API-маршрутов находится в `requests/requests.http` (формат расширения REST Client для VS Code); токены и идентификаторы копируются из ответов предыдущих запросов. Сценарии проверки безопасности автоматизированы в `requests/smoke.sh`.

Запускать smoke-проверку из корня репозитория:

```sh
./requests/smoke.sh
```

Скрипт требует `curl`, `jq`, Docker Compose и `.env`. Он показывает 404 при чтении чужой заявки, 400 при подстановке `owner_user_id/status/role` в тело создания, затем отдельно создаёт валидную заявку и запрашивает строку из PostgreSQL, проверяет 403 для привилегированной операции под USER, выполняет переходы статусов, выдаёт ровно один документ и проверяет доступ по владельцу. В конце проверьте письма в Mailpit и `docker compose logs worker`.

Дополнительные команды проверки:

```sh
docker compose logs --tail=100 api worker
docker compose exec db psql -U postgres -d documents -c "SELECT rolname, rolsuper, rolcreaterole, rolcreatedb FROM pg_roles WHERE rolname IN ('documents_app','documents_worker');"
docker compose exec db psql -U postgres -d documents -c "SELECT application_id,status,owner_user_id FROM applications ORDER BY created_at DESC LIMIT 10;"
docker compose exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged
```

Ожидаемый отказ проверки прав БД под app-ролью:

```sh
docker compose exec db psql -U documents_app -d documents -c 'DROP TABLE applications;'
```

Команда должна завершиться ошибкой прав. Не выполняйте `DROP` под `postgres`.

## 9. Известные ограничения

1. Интеграция LLM не реализована по прямому исключению задания ЛР №3.
2. Восстановление доступа использует локальную заглушку, которая выводит код в журнал API. Это допустимо для локальной лабораторной среды, но недопустимо для промышленной эксплуатации.
3. Документ генерируется как учебный текстовый артефакт (`text/plain`), а не как формат нормативно оформленной электронной справки. Конкретная электронная подпись и юридический механизм не заданы в ЛР №1–2 и не имитируются.
4. Брокер и SMTP обеспечивают обработку по модели at-least-once. Повторная доставка не создаёт новую запись notification на тот же outbox event, но теоретический сбой после успешного SMTP-приёма и до фиксации статуса может привести к повторной отправке письма.
5. TLS внутри изолированной локальной сети Compose не включён; стенд слушает опубликованные веб-порты только на localhost. Перед переносом на реальную инфраструктуру необходимы TLS, внешнее хранилище секретов, контроль миграций, резервное копирование и полноценная процедура управления ролями.

## 10. Файлы проекта

- `api/` — Go 1.25 REST backend и Dockerfile.
- `worker/` — Go 1.25 worker: outbox, RabbitMQ publisher/consumer и SMTP.
- `db/schema.sql` — DDL, индексы, ограничения и триггеры; основан на схеме ЛР №2 с одним документированным полем для дедупликации.
- `db/roles.sql`, `db/03_worker_role.sh` — минимальные права API и worker.
- `web/` — веб-клиент и reverse proxy Nginx.
- `requests/requests.http` — коллекция запросов ко всем endpoint, включая login/logout/recovery и разрешённую заглушку AI.
- `requests/smoke.sh` — end-to-end проверки основных защитных инвариантов.
- `docs/` — журнал изменений, карта кода, диаграммы фактической реализации, отчёт и справочные исходные схемы ЛР № 1–2 в `reference_l1/` и `reference_l2/`.
